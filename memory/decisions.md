# Decisions

Record meaningful project decisions and why they were made.

| Date | Decision | Reason | Consequence | Revisit? |
|---|---|---|---|---|
| 2026-10-03 | Build an independent engine and take inspiration only from open-source work. | Explicit user direction. | SUMO is a reference, not the simulation runtime; no upstream code copied. | On explicit scope change. |
| 2026-10-03 | Focus the product on Indian mixed traffic, including Bengaluru, Mumbai, and Hyderabad. | Explicit user interest. | Local demand/behaviour validation is needed; pilot region remains open. | When choosing the pilot. |
| 2026-10-03 | Bootstrap a packaged Python 3.12+ uv application. | User requested uv; a headless Python package supports inspectable experiments. | uv.lock and an editable local package exist; acceleration remains a profiling decision. | After performance measurements. |
| 2026-10-03 | Plan OSM network import and a separate optional Google Maps display adapter. | Current API capabilities and provider terms differ. | Persistent Google road extraction is not promised; account/workflow review precedes activation. | If suitable licensed access becomes available. |
| 2026-10-03 | Publish the project as a public GitHub repo named `population-simulator`, default branch `master`. | Explicit request from Sushrut. | First commit and remote exist (M0's 'no commits or remote' no longer holds). Local dir, package and CLI are still `traffic-simulator`. No licence file, so default copyright applies. | When the rename and licence are settled. |
| 2026-10-03 | Keep the local directory as `traffic-simulator`; only the GitHub repo is `population-simulator`. | Sushrut: "dont rename local folder". | Local paths, KB registry and Claude project dir stay valid. Package/CLI names were not discussed separately and are left unchanged. | If the package or CLI should match the repo name. |
| 2026-10-03 | Household commute burden measures time, money and income together (Sushrut: "should measure all... time, money income"). | Explicit user direction for the household-first questions. | Synthetic households need an income attribute; trips need monetary cost by mode as well as door-to-door time. Extended the same day: it also covers unpredictability and "all the issues", and should be realistic (Sushrut: "yes it covers unpredictable trip too.. all the issues.. make it realistic"). So reliability and crowding are in scope, and both per-trip and ownership costs count. The ownership-cost part is inferred from "all the issues" and should be confirmed. | When validation targets for realism are agreed. |
| 2026-10-04 | Life events happen within the simulated year, and each is a knob (Sushrut: "we shall add knobs for all of those"). Vehicle acquisitions follow observed regional data ("use the data of cars' sold or increase of registered vehicles in that region if possible"). | Mimic the population realistically. | Needs a life-events layer (vehicle purchase and sale, job change, moving, births and deaths, etc.) with data-backed default rates. Fixed-circumstances runs remain possible by switching events off. Registration data becomes a build input, so it can no longer be an independent check of vehicle growth unless part of it is held out. | When the life-event list for the first version is chosen. |
| 2026-10-04 | Life-event scope is **all** events (Sushrut: "all of these should be included.. even the children graduating primary, secondary, jr. college, sr. college.. marriages, move-ins, move-outs for job, etc"). | Realistic mimicry of the population. | The person/household model needs: vehicle buy/sell; job get/lose/change; moving house; births and deaths; marriage and leaving home; education stage transitions (primary → secondary → junior college → senior college); income changes; migration into and out of the region for jobs. The population is open at the region boundary (in- and out-migrants), so people accounting must cover born/died/moved-in/moved-out. | Build order only; scope is settled. |
| 2026-10-04 | Rename the Python package to `population_simulator`, the distribution and CLI to `population-simulator`; the local folder stays `traffic-simulator`. | Sushrut: "it should be population_simulator right? change this". | Supersedes the earlier note that package and CLI names were unchanged. Run with `uv run --locked population-simulator`. uv.lock was regenerated. | No. |
| 2026-10-04 | Adopt the engine/UI design: Python simulation engine (numpy arrays, multiprocessing pool, decide/resolve/commit days, keyed RNG), a runner process, a NiceGUI desktop UI, and one custom MapLibre + deck.gl map component, connected by the scenario schema, run-folder files and progress/cancel messages. | Sushrut asked for Python with multiprocessing; the throwaway map spike worked ("I love this"); he then asked to update the plan. | `docs/PLAN.md` and `docs/architecture.md` were rewritten around it. Open items: Windows/WebView2, snip drawing, offline basemap, performance at millions of points, Python 3.14 upgrade. | If Windows testing or scale tests fail. |
| 2026-10-03 / 2026-10-04 | Product direction: a desktop app for macOS and Windows (mobile and web out of scope) that models people's lives ("i want to model a person's life") for any map snip ("the cities doesnt matter"), with knobs for everything, simulating one year with a given population distribution and cross-checking simulated numbers against government numbers. | Sushrut's statements in the rubberduck session; see `scratch/direction-2026-10-03.md`. | Supersedes the corridor-first traffic plan; `docs/PLAN.md` rewritten 2026-10-04. | On explicit scope change. |
| 2026-10-04 | Never republish government data; publish only our statements of whether simulated numbers match ("we won't be republishing.. we will state that our simulation numbers match"). | Licence terms (MoSPI Category B, Census reproduction permission) and Sushrut's choice. | `govdata/README.md` rules: downloads stay in git-ignored `raw/`; only catalogue, manifests and comparisons are tracked; build data cannot back a "matches" claim. | No. |
| 2026-10-04 | Bengaluru is the first region; it gets the first local data pack. | Sushrut: "lets lock bengaluru as the region to start with". It has the richest open inputs of the three surveyed cities. | M1 fetches and checks Bengaluru first; the §9 smoke-test box is central Bengaluru. The study area (city corporation area, Bengaluru Urban district or a smaller snip) and the pack's contents are still to make (`docs/PLAN.md` §8). Under the any-region direction, this applies the 2026-10-03 India decision for data. | If Bengaluru inputs prove unusable from this machine or under their licences. |
| 2026-10-04 | Move to Python 3.14 (CPython 3.14.8, standard GIL build) and uv 0.12.23; `requires-python = ">=3.14"`, `uv_build>=0.12.23,<0.13.0`; relocked. Supersedes the 3.12+ row. | Sushrut: "lets upgrade python first". SPEC 0 drops 3.12 in 2026 Q4; NiceGUI supports up to 3.14; 3.15 was still rc3 and pyarrow, shapely and DuckDB had no 3.15 wheels. | `.python-version` is 3.14; the planned stack installs and imports on 3.14.8; the lock check also passes with uv 0.10.4. Settles M1-brief D8 and D9. The free-threaded build stays a later option. | When 3.15 wheels exist for the stack, or if NiceGUI native mode fails on 3.14 in M3. |
